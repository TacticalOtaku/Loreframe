# Loreframe M8 — Wiki Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Wiki article structure for long Journal content — title, subtitle, hero, intro, infobox (fixed and custom
rows; right/left/full/hidden), in-page contents, a long-form article region and related entries — without turning
the editor into a CMS (spec §19, §51 M8).

**Architecture:**
- *Article*: a `slot` region the author writes in with ordinary Foundry headings, paragraphs, links and nested
  Loreframe blocks. Nothing in it is generated after insertion.
- *Contents*: the document stores only an empty `nav[data-loreframe-contents]` with an editor hint. In view mode a
  `renderJournalEntryPageSheet` hook (fired after `_onRender`, `app.isView`) fills it from the article's headings
  (h1–h3 without `data-no-toc`, the rule Foundry's `buildTOC` uses) with buttons that scroll to the heading. It never
  goes stale and degrades to nothing when Loreframe is disabled. Foundry's sidebar ToC keeps working unchanged.
- *Infobox*: floated beside the text (classic wiki wrap). Fixed rows are text properties omitted when empty; custom
  rows are a rich-text table the author edits with Foundry's table tools. "Hidden" keeps the infobox in the document
  (no data loss) and hides it from readers with CSS — presentation only, not a secret (spec §22 concerns secrets).
- *Related entries*: the M7 `links` field.

**Spec:** §19, §28, §30, §31, §51 M8.
